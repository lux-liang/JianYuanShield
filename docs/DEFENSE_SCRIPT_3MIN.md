# 3 分钟答辩脚本（主叙事版）

## 0:00–0:25｜从争议现场开始

各位评委好，我们的作品是“鉴源盾”。

请设想这样一张 AI 图片：发布后被平台压缩、二次编辑、重新加水印，几周后卷入版权或虚假信息争议。此时文件哈希已经变化，元数据可能被删除，后加的水印还可能覆盖原水印。我们真正需要回答的，不只是“它像不像 AI”，而是：谁登记了它、登记了什么、传播后还能否核验、这条证据有没有被改。

## 0:25–0:50｜一句话讲清方案

鉴源盾把问题前移到内容发布之前，为 AI 内容建立一张可验证的“数字出生证”：

```text
创作者持钥登记
→ 主动水印与 AIGC 双重标识
→ 签名来源凭证
→ 传播后盲核验
→ 撤销与防回滚审计
```

系统分别回答四个问题：文件是否完全相同、水印是否恢复、标识是否完整、来源声明是否仍然有效。

## 0:50–1:20｜创新一：来源凭证不是自报身份

第一项创新，是创作者持钥的来源登记。创作者设备生成 Ed25519 密钥，私钥不离开设备；服务端签发一次性挑战，创作者签名后才能登记。登记记录把创作者公钥指纹、图片摘要、水印消息、模型权重和内容编号绑定在一起。

因此，即使图片被转码导致字节哈希变化，系统仍可通过 decode-only 的盲核验恢复登记消息；如果元数据被删除，也会单独报告标识损坏，不会偷换成“水印通过所以一切可信”。

## 1:20–1:50｜创新二：从单模型走向多平台协同

第二项创新，是 MEA 多水印冲突治理。现实中创作者工具、平台和取证机构都可能重复嵌入水印，而且 A 后写 B 与 B 后写 A 的影响并不相同。

我们用四模型 4×4 方向性矩阵，把“水印会不会互相覆盖”从概念变成可复算的部署策略。系统结合身份聚类 bootstrap 下界、最差方向恢复能力和画质约束，由后端实时推荐当前证据下的协同模型，而不是在前端写死一张推荐卡。

## 1:50–2:20｜创新三：让系统约束自己不能夸大

第三项创新，是 Claim-as-Code。比赛系统最容易出现的风险，是 PPT 使用一次最好看的数字，现场系统却换了代码、权重或阈值。

鉴源盾把每条正式声明绑定到协议、数据清单、checkpoint、逐图结果、统计实现和 release-core 签名。`ready_for_claims` 由现场证据动态计算；任一文件漂移，系统会把结论降级为 `review_required`，而不是继续展示旧数字。

这也是我们最希望评委记住的设计：系统不仅验证图片，也验证自己有没有资格说出这句结论。

## 2:20–2:45｜现场看到什么

现场我们会登记一张图片，生成内容编号和签名 sidecar；再验证被压缩和删除元数据的版本，展示字节、水印、标识和声明四种结论如何分离；随后撤销记录，让大家看到历史水印恢复事实仍被保留，但 `claim_valid=false`；最后在隔离副本中篡改一项证据，演示正式声明自动熄灭。

## 2:45–3:00｜主动交代边界并收束

我们不宣称可以识别任意未知 AI 图片，也不把完整性签名等同于法律采信。固定实验中暴露出的裁剪、旋转和部分换脸薄弱点都被原样保留，因为知道何时不能下结论，本身就是可信系统的一部分。

鉴源盾让 AI 内容从出生、传播到争议处置，都保留一条可恢复、可撤销、可审计、可复算的来源证据链。整条链经得起再次验证，这就是数字内容的可信身份。谢谢各位评委。

## 使用提示

- 主讲不要读代码路径和完整实验数字；评委追问时转入 `EVIDENCE_INDEX.md` 与 `JUDGE_QA.md`。
- `Deepfake proxy` 只作为传播流水线 smoke；真实换脸结论只引用固定 official SimSwap/LFW 证据。
- Ed25519 统一表述为“完整性签名”，不表述为“司法级证明”。
- 若现场只剩 90 秒，保留开场冲突、数字出生证、Claim-as-Code 和最后收束四段。
