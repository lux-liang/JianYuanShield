# 3 分钟答辩脚本（证据一致版）

各位评委好，我们的作品是“鉴源盾”，一套面向 Deepfake 传播链的可验证主动溯源与多水印冲突治理系统。

传统真假检测只能回答“像不像伪造”，却很难回答“观测内容能否匹配某条预登记来源记录、凭什么相信这条结论”。我们把问题前移：内容发布前就嵌入并登记来源凭证，传播后恢复凭证、匹配记录中的声明主体引用，再为核验事件生成完整性签名。

第一项创新是预登记来源记录绑定。保护接口为每份内容生成唯一消息和 content ID，绑定请求方声明的应用侧 `creator_ref`、原始内容哈希、保护内容哈希和 checkpoint 哈希。核验接口只做解码，不会重新嵌入，因此可以跨请求验证传播后的内容是否匹配登记记录。这里的 `creator_ref` 不是实名身份认证；租户、登录会话和对象所有权由部署身份系统建立。

第二项创新是 MEA 多重嵌入攻击协议。现实中平台或攻击者可能再次添加水印，覆盖原始来源信号。MEA 分别测量先嵌消息的保留率和后嵌消息的成功率。我们没有把 256 张图误当成 256 个独立身份：v2 从逐图证据重建 217 个身份簇，执行 20,000 次确定性 cluster bootstrap，并用覆盖 4×4×6=96 项的固定同步置信族做部署选择。不同模型的原始 bit accuracy 只作诊断，归一化 margin、协议成功率和画质聚类下界共同进入硬约束。矩阵出现失败不是要掩盖的缺陷，而是多水印共存的红队发现。

第三项创新是 Claim-as-Code。过去竞赛系统容易把小样本、模拟结果或不同指标写成一个漂亮数字。鉴源盾把每条声明绑定到 checkpoint 哈希、数据清单、样本量、指标、协议和原始 artifact；`ready_for_claims` 由现场证据与签名动态计算，任一闭包条件失败都不会发布为已验证结论。

现场我们将演示：输入声明主体引用并保护图片；得到 content ID；对图片做传播编辑；通过 decode-only 接口验证其是否匹配预登记记录；查看输入、输出和 checkpoint 哈希；最后篡改一条记录，展示 Ed25519 验签失败。

我们也明确作品边界：Deepfake proxy（`deepfake_proxy_v1`）不等于真实换脸；真实换脸只引用固定官方 SimSwap/LFW n256 的身份不重叠、四对照、条件迁移与签名证据。KAD-Net 在 clean-migrated 与 clean-and-watermarked-migrated 子集分别恢复 160/161、153/154，SepMark 为 151/161、150/159；这些分组由 raw rows 重算。由于生成与迁移测量使用同一 ArcFace checkpoint，我们称它为流程内迁移证据，不称独立身份验证器。Ed25519 是完整性签名，不自动等于法律采信。

鉴源盾的目标不是展示一排无法复核的高分，而是让每一次来源核验、每一次攻击评测、每一句科研结论都能追溯到证据。谢谢各位评委。
