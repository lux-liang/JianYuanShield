## 1. 编写目的

鉴源盾内容来源可信取证系统 V1.0 面向 AI 生成或合成图像的主动水印保护、登记来源核验、签名完整性记录与评测证据展示。本说明书给出软件定位、功能、运行环境、数据处理、安全边界及与第三方成果的关系，供登记申请、项目交付和后续运维使用。

## 2. 软件定位

普通文件哈希在图片被压缩、缩放或二次编辑后会变化，单独依赖可删除元数据也不足以建立稳定的登记联系。本系统在内容发布前嵌入主动水印消息，生成内容编号和签名来源凭证；在传播后对指定登记记录进行水印消息恢复和阈值匹配。

系统的主要对象是“已登记内容与某条登记记录是否匹配”，不是对任意未登记图片的开放世界真假鉴定。系统中的签名证明指定字节与签名密钥之间的完整性关系，不自动等同于实名认证、可信时间或司法采信。

## 3. 建设目标

1. 对经授权图像建立内容编号、水印消息、权重哈希和创建时间的登记关系。
2. 对传播后图像执行指定记录核验，将“字节完全一致”、“水印达阈值”、“标识完整”和“声明有效”分开表达。
3. 使用 Ed25519 对来源记录、凭证和审计事件执行签名与验签。
4. 以机器可读声明门禁绑定代码、协议、权重、校准产物和评测证据，证据不完整时关闭正式结论。
5. 为 Web、Android 和微信小程序提供统一的能力和边界表达。

## 5. 主要功能

### 5.1 运行状态与能力门禁

系统通过健康、GPU、证据、声明和模型状态接口分别反映进程可达性与业务可信性。一个模型只有在 `available` 、`registered`、`calibrated` 和 `trusted` 同时为真时才是 `provenance_ready`。

代码接口能够适配 LIDMark、KAD-Net、SepMark 和 WaveGuard，但“有适配器”不等于“已受信开放”。当前仓库的前端契约测试只把 KAD-Net 设为 `provenance_ready` 正例；实际部署必须以 `/api/models/status` 实时返回为准，本文档不声明其他三个模型已通过来源保护的受信门禁。

### 5.2 创作者密钥持有挑战

后端已实现有限时的一次性 Ed25519 挑战，挑战绑定创作者公钥指纹、应用侧引用、模型、原始图像 SHA-256、随机数和过期时间。Android 客户端已实现挑战请求、本地签名与保护提交。

当前 Web 与小程序的直连保护请求尚未提交 `challenge_id` 和 `creator_signature_base64`，因此不应被表述为完整的创作者持钥证明。后端在 `production` 模式下会拒绝缺少挑战的保护请求；在非生产模式下容许应用侧引用声明，但该声明不会变成实名认证。

### 5.3 主动水印保护与登记

系统校验图像大小和解码后像素数，在真实检查点上嵌入与内容编号关联的水印消息，生成受保护 PNG。数据库保存内容编号、创作者应用引用、模型、原始/保护文件哈希、检查点哈希、验证阈值和签名记录。原始上传图像不进入来源资产目录，但受保护图、来源记录和应用引用会持久化。

可选的 AIGC 图像标识功能写入可见标识、PNG `AIGC` 元数据和生产者签名封印。本项实现是工程字段和检查功能，合规结论仍取决于具体部署、输入和适用规则。

### 5.4 来源凭证和传播后核验

保护成功后生成 JSON 来源凭证，可与受保护图分开保存。核验时可使用内容编号、来源凭证或图片 AIGC 元数据定位记录；多个定位器同时出现时必须一致。系统恢复水印消息，计算模型规定指标，并分别返回：

- `exact_protected_file_match`：待核验文件与登记保护文件是否字节一致；
- `verified`：水印恢复值是否达到已登记阈值；
- `aigc_metadata_intact`：双重标识和签名封印是否完整；
- `claim_valid`：创作者证明、检查点、校准、签名、审计、撤销和证据门禁是否同时成立。

文件字节改变不必然意味着水印恢复失败；水印达到阈值也不必然意味着 `claim_valid=true`。

### 5.5 撤销与审计

对已完成持钥绑定的记录，系统可签发一次性撤销意图，由创建记录时的同一密钥签名后原子消费。撤销保留历史核验事实，同时使当前声明无效。

审计链使用顺序号、前驱哈希、事件哈希和逐事件签名，并用独立链尾锚点检查数据库回滚或尾部删除。SQLite 仍是单机存储，宿主机特权用户或卷写权限泄露仍会影响证据可信性，它不是分布式不可篡改账本。

### 5.6 评测证据与多水印冲突治理

系统提供固定协议的单模型鲁棒性评测、SimSwap 实验证据解析和 MEA 4×4 有向二次嵌入矩阵。`claims_manifest.v1.json` 为每项声明指定了必须存在的原始行、协议、实现、检查点与签名成员。文档或前端显示的历史数值不能替代运行时验证。

四种模型的消息长度、解码器和指标语义不同，系统不把它们的原始 bit accuracy 简单混成单一总分。MEA 策略是固定样本和威胁矩阵下的部署建议，不是对任意数据集和任意模型的普遍排名。

## 6. 典型业务流程

```text
运行状态检查
  → 选择 provenance_ready 模型
  → 客户端计算原图 SHA-256
  → 获取一次性挑战（正式持钥流程）
  → 客户端签名
  → 嵌入水印并建立登记
  → 下载受保护 PNG 和 JSON 来源凭证
  → 内容传播或受控变换
  → 上传待核验图片与编号/凭证
  → 分别解读 exact match、verified、metadata 与 claim_valid
```

## 7. 运行环境

### 7.1 服务端

- Python 3，FastAPI，Uvicorn；
- PyTorch、TorchVision、OpenCV、Pillow、NumPy 等图像与模型依赖；
- 真实模型推理依赖与当前锁定环境匹配的 NVIDIA GPU/CUDA；
- SQLite 来源记录库，文件系统资产与报告目录；
- Docker/Compose 可用于开发或生产形态组装。

精确依赖版本以 `requirements.lock`、Android Gradle 配置和供应链物料清单为准，不以本说明书的概括代替。

### 7.2 客户端

- 支持现代 JavaScript、Fetch API 与 Web Crypto 的桌面浏览器；
- Android 客户端使用 Kotlin 与 Jetpack Compose，release 构建只接受 HTTPS 节点；
- 微信小程序需配置合法 HTTPS 域名和运行时 `extConfig`。

### 7.3 网络与 TLS 边界

应用进程和容器内网关本身使用 HTTP 通信。仓库提供在边缘反向代理处终止 TLS、将明文 HTTP 重定向到 HTTPS 的 Caddy 配置。但配置文件存在不能自动证明某次在线部署的证书、域名和强制跳转已经验收。公网交付必须现场验证 HTTPS、HSTS、证书链、上传限制和反向代理传递头，不能使用明文 HTTP 上传用户图像或凭证。

| 类型 | 主要内容 | 处理说明 |
| --- | --- | --- |
| 图像输入 | 授权的原图或传播图 | 执行文件大小、解码尺寸和格式校验 |

| 审计输出 | 签名事件、锚点状态、声明和证据检查结果 | 是技术完整性材料，不自动具备法律效力 |

## 9. 已知边界

1. 只对已登记记录做指定水印匹配，尚无经校准的通用 blind detector；批量合规接口应返回 `capability_unavailable`，不得伪造合规率。
2. 公网 Web 已使用单管理员 HMAC 签名会话、CSRF 校验和登录失败限速；同源网关在服务端注入共享 API Key，浏览器不能读取长期密钥。这一双层边界仍不是多用户、角色、scope 或对象级授权系统，不能直接作为多租户权限模型。
3. SQLite 适合单机交付和竞赛原型，不是高并发多租户生产集群。
4. GPU 超时不能强制终止已启动的内核；当前槽位会保留至工作线程真正退出。
5. KAD-Net 和 SepMark 在固定正式协议的中心裁剪和 5° 旋转项上存在几何同步失败，不应被表述为对所有编辑稳健。
6. `deepfake_proxy_v1` 是确定性局部编辑代理，不是真实 Deepfake 模型实验。真实换脸材料只按其独立的固定 SimSwap/LFW 证据轨道解读。
7. 创作者持钥证明不是实名证明；系统时钟不是可信时间戳；签名和审计不自动保证司法采信。
8. 第三方模型、数据集、预训练权重和人物图像的许可与人格权由各自条款决定，不由本项目代码的权利状态覆盖。
