## 1. 设计目标与非目标

### 1.1 设计目标

- 对图像保护、来源登记、传播后核验、签名凭证和撤销建立统一的业务链。
- 将模型是否可用、权重是否登记、阈值是否校准、证据是否受固定签名者覆盖分别检查。
- 使系统可在证据缺失或漂移时 fail closed，而不是使用页面缓存或默认数字生成正式结论。
- 使不同消息长度、不同解码器语义的第三方水印模型可被统一编排，但不把不可直接比较的指标混合。
- 支持 Web、Android 和微信小程序共用后端 API，并让客户端按相同的可信字段解读结果。

### 1.2 非目标

- 不对任意未登记图像提供通用 AI/非 AI 判定。
- 不将应用侧 `creator_ref` 或 Ed25519 密钥持有证明当作自然人实名认证。
- 不将本地系统时钟当作可信时间戳，不将 SQLite 事件链当作分布式不可篡改账本。
- 不对司法采信、监管认定或模型在所有攻击下的性能作自动保证。
- 不重新声明 LIDMark、KAD-Net、SepMark、WaveGuard、MEA 或 SimSwap 底层算法为本软件原创。

## 2. 整体架构

```text
Web / Android / 微信小程序
            │
            │ HTTPS（公网边缘终止，需部署验收）
            ▼
同源静态/API 网关 ── 静态前端
            │
            │ 内网 HTTP + 服务端 API Key
            ▼
FastAPI 应用
  ├─ 上传/请求限制与鉴权
  ├─ 创作者挑战与登记/核验编排
  ├─ 模型适配器 ── 只读第三方模型源码/权重
  ├─ AIGC 标识与 Ed25519 签名
  ├─ 声明、证据和 MEA 策略门禁
  └─ SQLite + 受保护图/凭证/报告文件
```

系统采用单体 API 与独立静态网关的组合形式。真实模型源码、权重和评测数据位于仓库外受控运行时根目录，通过只读挂载提供给进程。只读只能约束容器写入，不证明挂载内容可信，因此还需要哈希清单、校准文件和签名证据。

## 3. 模块设计

### 3.1 应用入口与中间件

`system/backend/app.py` 创建 FastAPI 应用，按顺序组装请求体大小、请求并发、存储余量、API Key、限流、安全响应头和 CORS 中间件。生产模式禁用 OpenAPI 文档入口，并要求长度不少于 32 字符的 API Key 以及 HTTPS CORS origin。

健康接口只表示存储可写、鉴权配置就绪和剩余空间等运行条件，不把评测证据或模型可信性合并进简单健康状态。

### 3.2 路由与业务编排

`system/backend/routes.py` 定义健康、模型、评测、证据、保护、核验、撤销和审计 API。对 GPU 任务使用“运行槽 + 排队容量”两个信号量：

1. 请求进入时先获取有界容量；
2. 再获取单进程 GPU 运行槽；
3. 推理在线程池中运行并受总截止时间约束；
4. HTTP 响应超时时不立即释放 GPU 槽，而是等待底层工作线程真正退出，防止超时请求累积成隐藏并发。

这一设计仍不能强制杀死永久卡死的 GPU kernel，多副本的全局配额也需要外部任务队列或分布式配额。

### 3.3 模型适配器

在线与评测适配层封装以下契约：

- 检查模型源码和权重是否存在；
- 核对检查点 SHA-256；
- 在指定设备上构造模型并使用严格状态字典加载；
- 对 RGB 图像和二进制消息执行 `encode`；
- 对图像和目标消息执行 `decode`，返回模型自身规定的指标；
- 报告消息长度、主解码器、检查点和阻断原因。

当前支持的适配名称为 LIDMark、KAD-Net、SepMark 和 WaveGuard。适配器是本平台的编排代码；适配器加载的底层网络、训练代码和预训练权重归属上游。

### 3.4 模型可信状态

对每一个模型，系统单独计算：

```text
available = 适配器可用 且 当前权重字节哈希匹配
registered = available 且 权重命中 approved/verified 清单项
calibrated = registered 且 身份隔离校准产物通过重算
trusted = calibrated 且 权重/校准/清单受固定签名证据覆盖
provenance_ready = available 且 registered 且 calibrated 且 trusted
```

当前仓库契约测试的 `provenance_ready` 正例是 KAD-Net，这是本 V1.0 材料对“已受信来源保护”的保守口径。运行时状态取决于实际挂载和签名证据，任何文档不得硬编码替代 `/api/models/status`。

### 3.5 创作者挑战与密钥证明

挑战对象使用 `creator-identity-challenge.v1`，包含：

- 32 字节随机 nonce、挑战编号和过期时间；
- 创作者 Ed25519 公钥指纹和由其派生的 `owner_scope`；
- `creator_ref`、模型名和原始图像 SHA-256；
- 可选的服务端签名。生产模式消费挑战时要求该签名与固定公钥指纹一致。

客户端对 canonical JSON 签名。服务端核对所有绑定，验证创作者签名，然后使用条件更新原子设置 `used_at`，防止重放同一挑战。挑战 TTL 默认为 300 秒，配置只允许 1–900 秒。

后端与 Android 客户端已完成该流程；Web 与小程序当前的保护请求尚未提交挑战编号和创作者签名。因此设计上在生产模式必须拒绝它们的无挑战保护请求，而不是降级为伪持钥证明。

### 3.6 来源登记与消息派生

登记流程核心是 `system/backend/provenance.py`：

1. 检查生产模式密钥材料与创作者挑战；
2. 将上传图像按 EXIF 方向转换为 RGB；
3. 构造适配器，记录推理前检查点路径和 SHA-256；
4. 生成唯一 `content_id`；
5. 在已配置不少于 32 字符的 provenance secret 时，用 HMAC-SHA256 由内容编号、模型和计数器派生消息位；非生产兼容模式可使用存储的随机消息，但不能获得正式 claim；
6. 嵌入消息，再次检查运行中权重标识未变；
7. 生成 PNG，可选写入 AIGC 可见/隐式标识；
8. 原子写入受保护文件、SQLite 记录和创建审计事件；
9. 同步审计锚点并生成来源凭证。

任何数据库写入失败应回滚并删除本次新建的保护图，避免孤立资产。

### 3.7 AIGC 标识设计

`system/backend/aigc_labeling.py` 实现图像可见标识、PNG `AIGC` 文本元数据、内容编号绑定和生产者 Ed25519 封印。标识检查分别返回是否存在、密码学是否有效、签名者是否命中固定指纹。只有绑定编号、元数据和封印都成立时，记录级 claim 才可继续通过。

该模块提供技术字段和签名检查，不代替部署方对实际适用标识规则和合规流程的复核。

### 3.8 核验设计

核验输入是待核验图像与至少一种登记定位方式：显式 `content_id`、JSON 来源凭证或图像 AIGC 元数据。系统首先校验多定位器是否一致，再读取登记记录。

在调用模型前，记录加载逻辑对 SQLite 重复列与 `record_json` 中的内容编号、主体、模型、文件哈希、检查点和时间绑定进行比对。核验恢复结果与登记阈值比较，同时生成新的签名核验事件。

响应严格分开字节精确匹配、水印阈值匹配、AIGC 标识完整和总 claim 有效性，以防止客户端把单一布尔值扩大解读。

### 3.9 来源凭证与撤销

来源凭证是自包含 JSON，包含登记记录、创作者证明摘要、审计创建事件、锚点状态和撤销状态，并有独立的凭证签名。下载响应使用 `private, no-store` 缓存策略。

撤销分两步：

1. 服务端签发绑定内容编号、原因、nonce 和有效期的一次性意图；
2. 创作者用原登记密钥签名，服务端验证后原子消费并追加审计事件。

撤销后历史 `verified` 事实可保留，但当前 `claim_valid` 必须为假。

### 3.10 审计链与独立锚点

审计事件绑定顺序号、前驱事件哈希、对象负载哈希、事件哈希和 Ed25519 签名。文件形式的独立锚点记录链尾序号与哈希，用于区分精确匹配、数据库领先、数据库回滚、签名不可信等状态。

生产模式要求锚点完整可信。该设计可发现中间替换、顺序破坏、尾部删除和整库旧快照回滚，但如果攻击者同时掌握数据库、锚点和签名私钥，软件无法自行恢复信任。

### 3.11 证据与 Claim-as-Code

证据发布采用内容寻址清单，清单指定文件路径、大小、SHA-256、角色和签名配置。`claims_manifest.v1.json` 为每项声明列出证据、限制和动态 gate。运行时验证会检查原始行覆盖、数据清单、协议、检查点、实现哈希、release-core 成员和固定签名者。

清单对一组禁止文档表述也做静态检查，用于阻止无外部证据的绝对化首创、法律效力级别和性能绝对化表述。

### 3.12 MEA 多水印冲突策略

MEA 系统对四个登记模型执行有向二次嵌入矩阵。策略引擎不信任前端固定推荐，而是在运行时重新验证策略和证据五件套是否受 release-core 覆盖，重算原始行、身份簇、同步置信界、Pareto 可行集和选择稳定率。

输出是对固定威胁模型的风险建议，不自动执行双水印，也不取代单模型来源登记门禁。

### 3.13 跨端客户端

| 客户端 | 设计要点 | 当前限制 |
| --- | --- | --- |
| Web | 同源网关保持 API Key 在服务端，前端按 trust contracts 解读状态 | 直连保护表单未提交创作者挑战字段 |
| Android | Tink Ed25519 密钥、Keystore AES-GCM 包装、挑战签名、凭证与撤销 | 不提供自然人实名，没有证书 pinning |
| 微信小程序 | 强制标准 HTTPS 域名，本地历史每次重新计算可信门禁 | 长期静态 Key 不安全；保护请求未接入挑战 |

## 4. 主要数据结构

### 4.1 来源记录

`provenance-record.v2` 的核心字段包括：

| 字段组 | 主要内容 |
| --- | --- |
| 对象 | `content_id`、`creator_ref`、`owner_scope`、`created_at` |
| 创作者证明 | 挑战、公钥、客户端签名、指纹和密钥持有结果 |
| 文件绑定 | `original_sha256`、`protected_sha256` |
| 模型绑定 | 模型名、检查点 SHA-256、登记/校准状态 |
| 水印绑定 | 消息长度、消息哈希、消息保护方式、协议版本和验证阈值 |
| 标识 | 可选 AIGC 字段、可见标识和生产者封印状态 |
| 证据 | 记录 Ed25519 签名和签名者指纹 |

### 4.2 SQLite 存储

数据库包含来源记录、创作者挑战、核验事件、撤销意图/事件与审计账本。事务、外键和进程内锁用于单进程一致性，WAL 用于常规读写。

安全设计不信任数据库重复列本身，会将它们与签名 `record_json` 的绑定字段重新比对。然而 SQLite 无对象级权限、外部不可变存储或可信时钟，因此正式多租户产品需要替换或增强存储层。

### 4.3 文件资产

- `assets/provenance/{content_id}/protected.png`：受保护图；
- `assets/provenance/{content_id}/source-credential.json`：来源凭证；
- `reports/`：评测、统计、签名和 release-core 证据；
- `weights/`：仓库外权重、`WEIGHT_MANIFEST.json` 与校准产物；
- 审计锚点：按部署配置存放的独立签名链尾状态。

原始保护上传图不作为来源资产保存。受保护图和来源记录目前没有完整自动 TTL，需由部署方建立留存和删除政策。

## 5. 核心接口设计

| 方法 | 路径 | 职责 | 关键安全要求 |
| --- | --- | --- | --- |
| GET | `/api/health` | 最小健康探测 | 不暴露生产详细信息 |
| GET | `/api/models/status` | 返回模型来源保护门禁 | 客户端必须按四项门禁 fail closed |
| POST | `/api/creator/challenges` | 创建绑定图像和模型的一次性挑战 | 生产消费时必须验证服务端签名 |
| POST | `/api/provenance/protect` | 水印保护、登记、签名、审计与凭证生成 | 生产模式必须提交挑战与创作者签名 |
| POST | `/api/provenance/verify` | 按编号、凭证或元数据定位并核验 | 多定位器不一致必须拒绝 |
| GET | `/api/provenance/credentials/{content_id}` | 下载来源凭证 | 私有、禁止缓存；生产需对象级授权 |
| POST | `/api/provenance/records/{content_id}/revocation-intents` | 签发一次性撤销意图 | 只允许固定原因枚举 |
| POST | `/api/provenance/records/{content_id}/revoke` | 验证原创作者密钥并撤销 | 意图只消费一次，撤销后 claim 必须失效 |
| GET | `/api/provenance/audit` | 验证事件链与锚点 | 生产环境对不可信锚点 fail closed |
| GET | `/api/claims` | 动态验证声明与证据 | 不信任文档历史值 |
| GET | `/api/evidence/audit` | 检查签名 evidence set | 要求固定公钥指纹与精确成员 |
| POST | `/api/compliance/batch` | 批量合规能力契约 | 当前只返回 `capability_unavailable`，不生成合规率 |

完整字段契约以 `docs/API_CONTRACT.md` 为准。

## 6. 安全设计

### 6.1 输入安全

- 上传总大小、解码后像素、批量数、并发请求和请求体读取时间均有上限；
- 标识符使用严格白名单正则，文件下载使用根目录包含性校验；
- 图像在信任前经解码、格式和像素数检查；
- 来源凭证大小有限，未知或冲突定位拒绝。

### 6.2 鉴权与授权

生产模式强制 API Key，同源网关可在服务端注入 Key，避免浏览器获取长期秘密。但共享 Key 没有用户主体、角色、scope 或对象所有者绑定。随机 `content_id` 只降低盲猜概率，不能代替授权。公开多用户部署前必须引入用户会话、对象级权限与审计。

### 6.3 密码学设计

- Ed25519 对 canonical JSON 执行签名；
- 验签时从公钥本身重新计算 SHA-256 指纹，不信任签名对象自报指纹；
- 只有当实际指纹与部署方带外固定值一致时，正式 claim 才继续通过；
- 运行时私钥与 provenance secret 必须通过密钥文件或 secret store 注入，不进入源码、镜像或软著包；
- 当前文件私钥仍是进程可读的无口令 PEM，正式高保障部署需迁移至 KMS/HSM 或受审计密钥服务。

### 6.4 网络设计

容器内 API 与网关使用内部 HTTP，生产 Compose 默认把端口绑定在回环地址，由外部边缘反向代理终止 TLS。仓库已有 Caddy 配置用于 HTTPS 证书、HTTP 重定向、HSTS 和安全响应头，但运行时证书状态和实际网络拓扑不能从代码仓库自动得出，必须单独验收。

### 6.5 供应链

- Python 依赖由哈希锁定文件和 CycloneDX SBOM 记录；
- 容器基础镜像要求不可变 digest；
- 权重和校准产物必须命中 `WEIGHT_MANIFEST.json` 并受证据签名覆盖；
- 模型加载使用 `weights_only=True` 和严格状态字典，但它不能证明网络语义无后门，外部 Python 模型源码仍需独立审核与树哈希。

## 7. 错误和状态设计

受控错误使用非 2xx HTTP 状态与结构化错误对象。主要语义为：

- 401/403：鉴权或授权失败；
- 404：记录或产物不存在；
- 409：记录当前状态不允许操作，例如无有效持钥绑定的撤销；
- 413：请求体、图像、批量或凭证超限；
- 422：格式、字段、绑定或签名不合法；
- 503：模型、证据、存储、队列或信任依赖不可用；
- 504：推理超过截止时间。

客户端必须将错误保持为错误，不得使用实验数据、模拟响应或上一次成功值填充当前结果。

## 8. 测试设计

仓库 `tests/` 覆盖以下类别：

- 路由、健康、请求体限制、限流、路径遍历和安全响应头；
- 创作者挑战的绑定、过期、重放、签名与篡改；
- 来源保护、核验、记录绑定、校准、审计和撤销；
- Ed25519 签名、指纹、签名清单与篡改拒绝；
- 模型适配、攻击协议、指标语义、阈值校准与评测证据；
- MEA 4×4 矩阵、身份簇统计、策略和签名成员；
- Web trust contracts、小程序可信门禁与 Android 契约。

软著包工具的单元测试另外验证第三方模型目录、权重、数据、虚拟环境、日志、备份、密钥和人物/媒体文件在默认包中被排除，并对源码清单与 SHA-256 清单进行反向校验。

## 9. 部署设计与边界

开发 Compose 默认为 demo，只绑定回环地址，可不强制 API Key；它不是公网生产配置。生产 Compose 要求 digest 镜像、只读模型挂载、Docker secrets、固定签名指纹、精确 HTTPS CORS origin、非 root、只读根文件系统、去除 Linux capabilities 和 PID 上限。

边缘 Caddy 配置将历史 HTTP 入口重定向到 HTTPS，并在同一路径下提供前端和 API。这是可交付的配置设计，但仍需要对运行中证书、DNS、端口、防火墙、反向代理头和日志进行现场验收。

## 10. 可维护性与变更控制

- 模型名称、消息长度、主解码器和阈值从协议/运行时状态读取，避免前端自行推导；
- 评测运行与 canonical report 分离，只有通过覆盖、哈希和错误行检查才能晋级；
- 每次更改路由、数据库 schema、模型/攻击、阈值、签名、密钥、客户端存储、基础镜像或公网拓扑时，需重新执行威胁建模和负向测试；
- 对外声明必须随代码和签名证据同步变更，不得仅更新页面文案。

## 11. 后续演进建议

1. 为 Web 与小程序接入与 Android 同等的客户端持钥挑战，或在有认证用户会话的后端中定义受控代签流程。
2. 用 OIDC/短期令牌、角色和对象级授权替换共享 API Key 作为完整产品鉴权。
3. 将 GPU 推理迁移到可回收独立 worker 与有界任务队列，实现多副本全局配额。
4. 接入 KMS/HSM、可信时间服务和带外不可变审计存储，建立密钥轮换、吊销与双人审批。
5. 建立来源记录、受保护图、客户端历史、日志和备份的完整保留/删除机制。
6. 只有在独立 blind detector 获得正负样本校准和完整契约后，才能把批量合规功能从 `capability_unavailable` 晋级。
