# 鉴源盾竞赛主叙事

## 一句话定位

鉴源盾让 AI 内容从生成时就携带可验证的来源身份，在压缩、编辑、换脸和多平台重复加水印后，持续回答“谁登记、登记了什么、证据有没有被改、声明还能不能成立”。

## 1. 从一张被转发的图片讲起

一位创作者发布了一张 AI 辅助生成图片。图片被截图、压缩、二次编辑，又被另一个平台重新加水印。数周后，它出现在一场版权或虚假信息争议中。

此时传统方案会遇到三次失效：

1. 文件哈希失效：任何转码都会改变字节；
2. 元数据失效：平台可以删除或重写元数据；
3. 单一水印失效：后嵌入水印可能覆盖先嵌入水印，几何变换还会破坏同步。

争议处置需要一条可以复核的证据链：谁在何时以哪把密钥登记了哪张内容，使用了哪份模型权重，传播后恢复出了什么，记录是否被撤销，支撑结论的实验和代码是否仍是原来的版本。

这就是鉴源盾的起点。

## 2. 一条贯穿内容全生命周期的闭环

鉴源盾把主动水印、来源凭证、合规标识、审计签名和多水印冲突治理串成一条闭环：

```text
创作者持钥登记
→ 四模型主动水印
→ AIGC 显式/隐式标识
→ 自包含签名来源凭证
→ 传播后盲核验
→ 撤销与防回滚审计
→ 多水印冲突策略
→ 声明证据门禁
```

这条链上每一环都回答一个不同问题：

| 环节 | 回答的问题 | 没有它会怎样 |
|---|---|---|
| 持钥登记 | “登记者是否真的控制创作者密钥？” | `creator_ref` 只是可伪造文本 |
| 主动水印 | “内容变化后还能否恢复登记消息？” | 文件哈希一变化就失效 |
| 双重标识 | “是否满足机器可读与人眼可见标识？” | 只有水印、没有合规表达 |
| 签名凭证 | “记录是否完整且未被篡改？” | 服务端数据库成为单点信任 |
| 防回滚审计 | “历史是否被删尾、替换或回滚？” | 单个签名无法证明事件顺序 |
| 双签名撤销 | “创作者能否撤回声明且保留历史事实？” | 删除记录会破坏审计连续性 |
| MEA 治理 | “多个平台重复嵌入时应该选谁？” | 只证明单模型有效，无法部署 |
| Claim-as-Code | “页面上的结论是否仍被当前证据支撑？” | 报告数字与运行系统可能漂移 |

## 3. 三个递进式创新

### 创新一：从“文件指纹”走向“内容来源凭证”

我们不把 SHA-256 当作传播后的唯一判断依据。系统把创作者公钥、原图摘要、模型消息、checkpoint 指纹、内容编号和审计事件绑定为签名凭证。文件被转码后，字节匹配可以失败，但水印恢复与来源声明仍可分别核验。

这里的关键设计，是把结论拆成四种互不混淆的语义：

- `exact_protected_file_match`：是否还是登记时的原始输出字节；
- `verified`：是否恢复出登记消息；
- `aigc_metadata_intact`：标识与生产者封印是否完整；
- `claim_valid`：身份、权重、阈值、证据、审计与撤销门禁是否同时成立。

### 创新二：从“单模型鲁棒性”走向“多平台水印冲突治理”

现实不是一张图只经过一次水印。创作者工具、内容平台、社交平台和取证机构都可能重复嵌入。后写入者对先写入者的影响具有方向性，A→B 与 B→A 不能合并。

鉴源盾用四模型 4×4 方向性 MEA 矩阵，把“会不会互相覆盖”变成可复算的部署决策。系统不仅看平均准确率，还看身份聚类 bootstrap 下界、最差方向 margin、最差攻击成功率和图像质量，并由后端实时重算策略。

这使项目从“模型展示”提升为“跨平台协同治理”。

### 创新三：从“写在 PPT 里的数字”走向“运行时可验证声明”

比赛作品最容易出现的问题是：PPT 使用最好看的一次实验，系统运行的却是另一份代码、另一份权重或另一套阈值。

鉴源盾把声明本身做成机器可验证对象。每项正式结论绑定：

- 协议版本和攻击集合；
- 数据清单与逐文件哈希；
- checkpoint 与校准证据；
- 逐图原始行和统计实现；
- release-core 文件集合；
- 固定 Ed25519 签名者。

任何一个对象漂移，结论立即降级为 `review_required` 或 `blocked`。这就是 Claim-as-Code。

## 4. 为什么四个模型不是简单堆砌

四个模型分别代表不同技术路线、消息容量和运行语义。统一 adapter 只统一加载、设备、错误和证据结构，不把不同 decoder 的数值粗暴平均成“总准确率”。

| 模型 | 在故事中的角色 |
|---|---|
| KAD-Net | 当前高可靠主保护模型与换脸迁移主证据 |
| SepMark | 多水印协同条件下的推荐策略 |
| LIDMark | 身份字段与水印联合恢复路线 |
| WaveGuard | detector/tracer 分离路线，同时诚实暴露薄弱边界 |

我们的优势来自对四个模型可信区间、失效边界、组合策略和发布条件的系统掌握。

## 5. 评委应当记住的三个画面

### 画面一：内容出生时拥有“数字出生证”

创作者设备生成密钥，签署一次性挑战。系统保护图片、写入合规标识、生成签名 sidecar，并登记审计链。服务端从未拿到创作者私钥。

### 画面二：图片变了，但来源证据没有混成一句话

上传被压缩的图片：字节匹配失败，水印恢复仍可能通过；删除元数据：标识完整性失败；撤销记录：历史恢复事实保留，但 `claim_valid=false`。四类结论同时展示，让评委看到系统没有偷换概念。

### 画面三：改一份证据，整条声明自动熄灭

演示 evidence gate：当 summary、checkpoint、协议或签名任一不一致时，页面不再显示“正式结论”，而显示需要复核。恢复签名证据后，声明重新成立。

第三个画面是项目区别于普通水印 Demo 的关键。

## 6. 如何讲实验结果

实验不按“我们准确率最高”展开，而按三个问题展开：

1. 能不能恢复：固定 LFW 15 攻击协议验证传播鲁棒性；
2. 会不会认错：SimSwap/LFW 使用 registered-positive 与三类负控，分开报告 TAR、FAR 和 Wilson 区间；
3. 能不能协同：MEA 4×4 验证重复嵌入的方向性影响并生成部署策略。

必须主动展示失败边界：KAD-Net、SepMark 在裁剪与旋转下存在同步失败，WaveGuard 在换脸控制中区分能力有限。承认这些边界不会削弱项目，反而证明系统的证据门禁有存在价值。

## 7. 三分钟答辩的情绪曲线

```text
争议现场的无力感
→ 传统证据三次失效
→ 鉴源盾建立出生证和证据链
→ 多平台重复水印的新矛盾
→ MEA 给出治理策略
→ Claim-as-Code 让每句话都能验
→ 现场篡改证据，系统主动拒绝背书
→ 结尾：可信来自一条经得起复核的证据链
```

## 8. 收束句

推荐答辩结尾：

> 鉴源盾让一份 AI 内容从出生、传播到争议处置，都保留可恢复、可撤销、可审计、可复算的来源证据。整条证据链经得起再次验证，这就是数字内容的可信身份。
